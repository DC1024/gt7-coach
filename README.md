# GT7 赛道工程师（Race Engineer）

给 PS5《GT7》当**实时副驾**：盯着遥测数据，在你该被提醒的时候说一句话。

不是事后剪辑解说，是**边开边说**。配合 [GT7 Dash](https://github.com/DC1024/gt7-dash)
（遥测接收 + 仪表盘）一起用；也能对着任何实现了 GT7 Dash 公开 v1 接口的服务跑。

**宣传页**：<https://dc1024.github.io/gt7-coach/> —— 一页看完它能做什么、
怎么做到的、以及做不到什么。

> **状态：v1.0.0-beta.1 —— 本地闭环 + 可选云措辞，14 条播报规则全部上线，
> 且每条规则都有独立开关、打滑/出界阈值可三档预设。**
> 判断、数字、时机**全部在本地确定性代码里完成**；云只做两件可选的事 ——
> 把结论润色成人话、给它一个嗓子。**两件都不配也全功能可用**：
> 这个服务在断网的车库里照样工作，只是措辞回到本地模板。

## 快速开始

```bash
# 1. 自检：用内置的合成赛道跑一遍，不连任何东西
python -m gt7coach demo
open http://127.0.0.1:8788/          # 自带验证页，按一下就能开语音

# 2. 接真车
python -m gt7coach serve --dash http://192.168.43.18:8787

# 3. 排障：跑几次 tick，把状态打到 stdout
python -m gt7coach once --dash http://192.168.43.18:8787
```

纯标准库，Python 3.10+，不需要 `pip install` 任何东西。

## 与 GT7 Dash 的接口

两个仓库**只通过 HTTP 契约耦合**，各跑各的进程，可以跨机器。

### 一、走出去（Coach → Dash）：只读公开 v1 接口

| 用途 | 接口 | 频率 |
|---|---|---|
| 当前帧 | `GET /api/v1/live` | 10 Hz |
| 找正在录制的场次 | `GET /api/v1/sessions`（看 `live` 字段） | 无参考圈时 2 s / 有之后 15 s |
| **参考圈剖面** | `GET /api/v1/sessions/<f>/profile` | **仅在参考圈需要换时**（换场 / 最快圈刷新） |

关于 `/profile`，两点必须说清楚：

- 它是 GT7 Dash 侧**已有分析能力的打包出口**（`clean_laps` / `lap_samples` /
  `find_peaks_valleys` / 距离重采样），一次返回「几何折线 + 等距遥测 +
  刹车入点/弯心/给油点」。消费方自己重写一遍不仅费力，还会因为实时侧只有
  10 Hz 轮询而精度更差、第一圈完全没有参考。
- 它的距离轴是**几何弧长**（相邻坐标弦长累积），不是速度积分。速度积分
  一圈漂移 60~300 m，拿它做「本圈 1200 m vs 参考圈 1200 m」对齐会差十几米，
  刹车点预告直接指错位置。

**这个端点是可选的。** 拿不到时 Coach 自动退回「自己拿实时帧攒参考圈」，
代价是第 2 圈起才有参考、精度 10 Hz。`CoachState.stats.ref_source` 会如实
写 `"profile"` 还是 `"self"`，`warnings` 里也会说明 —— 不允许静默降级。

### 二、走进来（Dash → Coach）：教练自己的 HTTP 接口

默认监听 `8788`（紧挨 Dashboard 的 `8787`，不抢）。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/coach/state` | **电平**：完整状态，每次都返回当前该说的 |
| GET | `/api/v1/coach/say` | **边沿**：只给还没播报过的，取走即清空 |
| GET | `/api/v1/coach/history` | 最近播报（`?n=20`） |
| GET | `/api/v1/coach/config` | 当前阈值配置 |
| POST | `/api/v1/coach/config` | 改阈值，`{"gate": {"max_per_lap": 3}}` |
| GET | `/api/v1/coach/health` | 存活 / tick 数 / 参考圈状态 |
| GET | `/` | 自带验证页（不依赖仪表盘就能听） |

全部带 `Access-Control-Allow-Origin: *`（仪表盘是另一个源，没有 CORS 头
浏览器会直接拦掉）。

**为什么两种语义都要有**：电平适合轮询式前端（不关心漏没漏，看当前状态就行）；
边沿适合播报场景（播完就得忘掉，不用前端自己写去重）。只给一种，就会逼消费方
写一个和这里重复的逻辑。

`state` 的完整结构见 [`gt7coach/contract.py`](gt7coach/contract.py) ——
那份文件就是契约本身，字段**只加不改**，破坏性改动必须升 `COACH_API_VERSION`。

```jsonc
{
  "api_version": 1,
  "connected": true,
  "ref_ready": true,          // 参考圈是否就绪
  "ref_lap": 3, "ref_len_m": 3769.6,
  "lap": 4,
  "s_m": 1240.5,              // 本圈已跑距离（沿参考圈的弧长）
  "delta_s": -0.213,          // 相对参考圈的时间差，负 = 更快
  "ref_speed_kph": 178.2,
  "next_brake_m": 96.4, "next_brake_s": 1.7,
  "say": [                    // 这一 tick 决定要说的话（通常 0 或 1 条）
    {"key": "brake_warn@1300", "text": "1.7 秒后重刹区，参考最低 92",
     "short": "准备刹车", "priority": 1, "evidence": {"t_go_s": 1.68}}
  ],
  "spoken": [ /* 最近播报历史 */ ],
  "stats": {"ref_source": "profile", "lateral_m": 1.2,
            "wheel_radius_m": {"front": 0.3391, "rear": 0.3435}}
}
```

### 三、语音

**默认让浏览器念**（`speechSynthesis`，Web Speech API）：零成本、零依赖、
零网络，首字延迟 ~0.1 s。音色偏机械 —— 但赛道工程师本来就该是短促无线电味。

Coach 自己不出声，只给文本；**出声是消费方的事**。README 顶部的
`http://127.0.0.1:8788/` 验证页里有最小实现可以直接抄。

## 三条设计原则

后面所有取舍都服从这三条。

### 1. 判断在本地，措辞在云上

| 环节 | 谁做 | 为什么 |
|---|---|---|
| 该不该说、说的是哪个数 | **本地代码** | 毫秒级、零成本、不会编数字 |
| 把结论变成一句人话 | 本地模板（R2.1）→ 云 LLM 润色（R2.2，可选） | 只有这里有增量价值 |

反过来（让 LLM 看着遥测自己判断）必翻车：一次调用 0.5~2 s，250 km/h 时
2 秒 = **139 米** ——「T1 刹车点提前 10 米」晚 139 米就是废话；而且 LLM 会编数字。

R2.1 已把这条原则落成代码：`rules.py` 判断、`phrases.py` 措辞，
**数字白名单是两边共用的同一把尺**（`fact_allow()`）—— 云润色插进来之后，
"云编数字"和"模板编数字"会走同一个检查，而不是两套漏法。

### 2. 按延迟分档，硬实时档禁止走云

| 档 | 延迟预算 | 生成 | 触发 |
|---|---|---|---|
| A 硬实时 | < 300 ms | 本地规则 | 刹车点 / 弯心 / 给油 / 打滑 / 出界 / 换挡 / 胎温 |
| B 圈后 | < 2.5 s | 本地算 + 云润色 | 每圈结束的 delta 与归因 |
| C 问答 | < 3 s | 云 LLM | 用户主动提问 |

R1 把 A 档和 B 档的本地部分都做完了。

### 3. 不打扰优先于多说话

一个话痨副驾比没有副驾更糟。四道闸：

1. **同类冷却** 20 s、**跨类冷却** 6 s（更紧急的话可缩短到 2 s 插队）
2. **弯中禁言**：`|G| > 0.8` 时只念 `short`（≤ 4 字），没短句就干脆不说
3. **每圈上限**：非紧急播报 6 句
4. **只报新信息**：同一个 key 每圈只报一次；key 里带位置标识
   （`brake_late@400`），于是天然是「同一个弯只提醒一次」

## 措辞层（R2.1）

`rules.py` 判断「**什么时候说、事实是什么**」，`phrases.py` 只回答「**怎么说**」。

```
rules.py     → facts dict（数字全在这）   ← 判断
phrases.py   → str（纯函数，不 import rules） ← 措辞
```

拆开是为了 R2.2：将来云润色插的正是这一层的位置 ——
**模板优先 → 云润色 → 失败回落模板**。接口定死成 `phrases.render(key, facts)`，
接云时 `rules.py` 一行不动。

| key | 升级前 | 升级后 |
|---|---|---|
| `lap_summary` | `1:23.45，比参考慢 0.42` | `1:23.45，慢 0.42` |
| `sector_loss` | `S2 慢 0.31` | `S2 慢 0.31，还差 0.80` |
| `next_focus` | `下一圈重点：T1，最近亏 0.40` | `T1 连续 3 圈慢 0.40，注意刹车点` |
| `fuel_range` | `还够 2.3 圈` | `油还够 2.4 圈` / `油只够 0.8 圈，这圈进站` |
| `projected_lap` | `预计 1:22.80` | `预计 1:22.800`（**不加比较**，见下） |

四条硬约束（全部有测试守着）：

1. **不产出数字** —— 句子里每个数都要能在 `evidence` 里找到。
   `phrases.fact_allow()` 是白名单本体，**本地模板与 R2.2 的云润色共用同一把尺**，
   否则"云编数字"和"模板编数字"就成了两套漏法。
2. **不做算术** —— 本层只念 facts 里的数，一个数都不许自己算。
   实测就是"本地偷偷算一个不在 facts 里的差值"让那把尺当场失效。
3. **不推断失误模式** —— "刹车早一点"这类处方需要驾驶模型，本地给不出。
   `next_focus` 的「注意刹车点」是**证据驱动**的固定提示
   （只在刹车区窗口损失占比 ≥0.5 时出现），不是猜。
4. **有长度预算** —— 预算**由 ttl 容量反推**（`TTL_CAP_S × 4.5字/s × 0.9`），
   P_LOW ≤8 字、P_NORMAL ≤8 字（B 档兜底），单句豁免（`lap_summary`≤20、
   `sector_loss`≤20、`next_focus`≤24、`fuel_range`≤24）；
   超预算在**写文案时**砍，**不能运行时截断**（截断会把 `0.37` 切成 `0.3`，
   那本身就是"编数字"）。

### 长度预算与 `ttl_s` 为什么是**一套**数字

`ttl_s` 的契约定义是"过期作废，免得攒到出弯再播一条旧消息"，
但它此前**没有任何消费者**。R2.1 把句子加长之后，"2 秒有效期 vs 4 秒语音"
这种矛盾就出现了 —— 一旦补上过期检查，第一批发不出声的就是这几句
（最恼人的失败：屏幕上什么也没错，就是不说话）。

曾经把"句子长度预算"和 `ttl_s` 写成两个独立常数，于是必然分叉：
`lap_summary` 预算允许 24 字（≈5.33 s）而 ttl 只有 5.0 s ——
预算允许的"最坏句子"比 ttl 还长。修 `brake_warn` 时**被实测打脸**：
原句「1.4 秒后重刹区，参考最低 90」＝17 字≈3.8 s 语音，ttl 只有 1.2 s；
改成 `max(speech_s(text), t_go + 0.6)` 之后又发现写死下限 `1.2 s` 本身是错的：
`brake_warn_s = 1.5` ⇒ t_go ≤1.5 ⇒ `t_go + 0.6` ≤2.1，而 8 字句需 1.78 s，
**在 t_go ≤1.0 时下限只剩 1.2 s 装不下** —— 即"最常见的接近窗口全程静默"。

现在单一事实源是 `phrases.TTL_CAP_S`（每个 B 档 key 的信息有效期秒数），
预算 = `容量 × 语速 × 0.9`；`phrases.ttl_for(text, priority, key)` 统一算 `ttl_s`
= `max(信息有效期, 这句话的语音时长 + 缓冲, 预算时长)`。
**"改文案"不再需要同步改 ttl** —— 分叉从源头消失。
TTS 语速常数与长度预算共用 `phrases.CHAR_PER_S`，所以"不超预算"和
"不超 ttl"两件事不会各说各话；`tests/test_rules.py::TestTtlFitsSpeech`
用 rules **真实产出的** Utterance 逐句校验，`test_phrases.py::test_every_budget_fits_its_ttl_capacity`
锁死"预算允许的最坏句子一定装得进 ttl 容量"。

### 为什么 `projected_lap` **不加**"快/慢多少"

试过，撤回了，记下来免得再试一遍：拿**参考圈**做基准，
`projected - ref_lap` 恒等于已经在同一圈播过的 `delta`（纯重复）；
拿**你自己最好圈**做基准，会和按参考圈口径说的 `lap_summary`（"慢 0.50"）
在同一次播报里互相打架（"慢 0.50" 之后紧接 "还快 2.09"）。
**同一圈里出现两个基准 = 玩家不再相信任何一句。**

### 为什么白名单测试要跑**完整引擎**，而不是只手搓 facts

`tests/test_phrases.py::test_no_invented_numbers` 喂的是手工构造的 facts，
facts 自己写的当然自洽 —— 它测的是"phrases 不编数字"，**测不到 rules
忘了往 evidence 里写字段**。真事：`_brake_warn` 算了
`over = speed_kph − v_ref`、句子说「快 57，准备重刹」，但 `over` 从没进
evidence。合成数据下永远绿，**真车场次回放**才被白名单抓出来。
所以 `TestEverySpokenNumberIsInEvidence` 必须**跑完整引擎扫全部播报**。

## 会说什么（R1 全部实现）

| key | 档 | 触发条件 |
|---|---|---|
| `off_track` | P0 | **双重确认**：距参考线横向偏离 + 轮胎打滑同时成立才报（单靠横向误报太多，实车验证后改的判定） |
| `slip_front/rear/all` | P0 | 滑移率超阈值持续 0.25 s（半径在线自标定）；**三档预设**（严格/标准/宽容）+ 滑块微调，仪表盘面板可调 |
| `brake_late@<刹车区>` | P0 | 已过刹车入点 > 8 m 还没踩刹车（只算到弯心为止） |
| `brake_warn@<刹车区>` | P1 | 距下一个刹车入点 < 1.5 s（比参考快时额外提示） |
| `shift` | P1 | rpm ≥ 换挡灯上限持续 0.5 s |
| `apex_slow@<弯心>` | P2 | 弯中速度比参考低 > 5 km/h |
| `throttle_late@<弯心>` | P2 | 过弯心 40~120 m 油门仍 < 0.3 持续 0.5 s |
| `tyre_hot` / `tyre_cold` | P2 | 任一胎温 > 110 / < 60 °C 持续 2 s。**报实际温度**（`左前胎 52 度太凉…`），太凉还给目标区间 80~100 °C（GT7 遥测不暴露天气 / 赛道温度，故用固定领域值）|
| `delta` | P3 | 本圈 delta 首次跨过 ±0.2 s |
| `projected_lap` | P3 | 跑过本圈 35% 后预测最终圈速（`参考圈速 + 当前 delta`）|
| `lap_summary` | P3 | 每圈结束报上一圈成绩与参考差（R2.1：`1:32.412，慢 0.37`）|
| `sector_loss` | P2 | 圈后：指出相对「本场各段最好值」最慢的那一段，并给还差多少（R2.1：`S2 慢 0.31，还差 0.80`）|
| `fuel_range` | P2 | 圈后：按本场油耗中位数算还能跑几圈（≤3 圈才提醒；≤1 圈给行动建议）|
| `corner_habit@<弯>` | P2 | **跨圈累积**：同一个弯连续 3 圈中位亏 ≥0.3s 才提醒，之后隔 3 圈再说 —— 这是教练区别于仪表盘的地方：仪表盘告诉你**现在**，教练告诉你**你的习惯**（R2.1：`T3 连续 3 圈慢 0.40，注意刹车点`）|

⚠️ 注意两套命名：**播报 key**（`Utterance.key`，上表第一列，含位置标识用于闸门去重）
与**措辞名**（`phrases.RENDERERS` 的键，如 `corner_habit@T1` → `next_focus`）
是不同的 —— 同一个措辞可以服务多个播报 key。

🔴 上表里 P0/P1 是 **A 档（硬实时 <300 ms）**，永远走本地模板、句子 ≤8 字；
P2/P3 是 **B 档**，将来（R2.2）可交给云润色。所有句子都过
`phrases` 的数字白名单与长度预算 —— 表格里的数字是**实测**，不是设计稿。

### 本地能算到什么程度（R1.5）

「不上云」不是把功能砍掉，而是把能本地算的都算完。下面这些**一个接口都不用调**：

| 能力 | 怎么来的 | 为什么不用服务端 |
|---|---|---|
| 分段用时（S1/S2/S3）| 从实时帧的几何弧长按**绝对距离**等分，边界插值 | Dash 的 `/sectors` 每次要重解析整场 jsonl（直播文件一直在变，一场 20 万帧要 2s+ 且越来越贵）|
| 理论最快圈 / 潜在空间 | 本场各段最好值之和 vs 实际最快圈 | 同上 |
| 每圈油耗 / 还能跑几圈 | 圈首圈尾剩余量做差，取近 5 圈**中位数** | 单圈油耗会被慢车/暖胎圈带偏，中位数才稳到能据以决策 |
| 预测圈速 | 参考圈圈速 + 当前 delta | 无线电里最常被问的一句 |
| 轮胎半径自标定 | 自由滚动帧上累计 `Σ(v·ω)/Σ(ω²)`，**前后轴分开** | 实测前 0.3391 / 后 0.3435，合成一个会变成固定偏置 |
| 跨场次历史最快圈 | 场次列表里已有的 `best_lap_s` + **几何形状比对**确认同赛道 | 不用赛道识别（实测 10 场只有 2 场已识别）|

本地分段与 Dash 服务端 `/sectors` 的交叉验证：同一圈 3 段分别
`[33.36, 36.00, 31.63]` vs `[33.379, 35.935, 31.677]`，**每段差 ≤0.07s**。

### 为什么没有"提问通道"（R4，已评估后砍掉）

把 12 个候选问题逐个核对「教练有没有主动说 / 直播页有没有显示 / 详情页有没有显示」之后，
**9 个已经有现成实现**（教练每圈说的成绩与最慢段、直播页的四轮胎温/油量续航/实时 delta/
下一刹车点、详情页的分段计时 · 理论最快圈），真缺口只剩 1 个——
而它已经被 **R1.6 每弯累积失误** 以正确的方式（主动播报）解决了。

推导过程见 `../2026-10-07-02-04-04/R4预设问题与必要性分析_2026-10-09.md`（若在同级工作区）。

### 离线调参（不用上车）

```bash
python -m gt7coach replay 场次.jsonl
python -m gt7coach replay 场次.jsonl --conf brake_late_m=12 --conf gate.max_per_lap=8
python -m gt7coach replay 场次.jsonl --json > a.json   # 调完再跑一次 diff 就知道改了什么
```

拿历史场次跑一遍，直接打出「会说的话」列表 + 逐圈统计 + 闸门丢了多少候选。
阈值以前只能上车试，而"感觉不太对"既慢又没法对比；现在改一个数跑一遍即可。

它第一次跑真实场次就抓出两个**实时侧永远看不到**的 bug：
`lap_buffer` 按帧数裁剪（实时 10Hz 够 300s，但 jsonl 60Hz 只有 50s，装不下一圈），
以及拿菜单帧（`lap=0`）自攒出 390m 的假参考圈把后面全带歪。

### 数据边界（诚实清单）

GT7 遥测是**单车流**，有些东西就是拿不到，不许编：

| 缺口 | 后果 |
|---|---|
| 只有你一台车的数据 | ❌ 不能说「Hamilton 在你后面 0.8 秒」。只能说名次 |
| 胎压 / 胎耗（格式 A 恒为 0） | ❌ 不能说「胎耗 12%」。只能说胎温 |
| 协议没有转向角 | ✅ 已用曲率 `κ = G_lat·g/v²` 替代（半径 + 左右） |
| 没有赛道里程碑 | ❌ 不能说「100 米标刹车」，只能说「1.5 秒后重刹区」 |

## 开发

```bash
python -m pytest tests/ -q      # 743 项，纯标准库 + pytest
```

测试用**合成赛道**（`gt7coach/synth.py`）而不是真数据 —— 合成圆上每个量都能
手算：圈长 = 2πR、横向 G = v²/(R·g)、刹车区起点就是减速段起点，断言于是能
写成等式，而不是「看起来对」。

几条踩过的坑，都写进了对应位置的注释与测试：

- 闭环折线在起跑线上是同一个点，而游戏的圈计时器与位置**不同步**：
  过线那一帧位置已进新圈（`s≈0`）但圈计时还是上圈的 69.70 s，
  两边相减就是「丢了一整圈」的假 delta（实测 +69.700 s → 修正后最大 0.116 s）
- `brake_late` 必须限制到弯心为止，否则会在出弯直道上报「刹车晚了 155 米」
- 合成帧里 `t` 必须**跨圈单调**（只有 `lap_time_s` 每圈归零），
  与记录器一致；否则回放时冷却永不生效
- 夹具改了速度就必须同步改轮速（`ω = v/R`），不然会造出「四轮抱死」的假象
- **白名单必须跑完整引擎**：只手搓 facts 测不出"rules 忘了把数字写进 evidence"。
  `_brake_warn` 的「快 57」漏了 `over_kph`，合成数据下永远绿，
  真车回放才被 `invented_numbers` 抓出来 —— 见
  `TestEverySpokenNumberIsInEvidence`
- **`ttl_s` 写死下限会静默丢掉消息**：`max(1.2, t_go+0.6)` 在
  `t_go ≤1.0`（最常见的接近窗口）装不下 8 字句（1.78 s）。
  ttl 必须 `max(speech_s(text), t_go+0.6)`
- **单点 delta / 圈差必须有硬上界**：参考圈一旦错配（不同赛道 / 半圈 / 被污染），
  `_delta` 会蹦出"比参考圈快 40 秒"之类的离谱值，摧毁可信度。规则层与显示层
  共用 `DELTA_MAX_S = 20 s` 这把尺；`lap_summary` 的 `vs_ref_s` 也用同一上界。
- **比赛终局判定不能看「上一圈」**：`c.lap.lap`（刚跑完那圈）在有固定圈数的
  比赛里最多到 `laps_in_race-1`（GT7 冲线后圈号不再自增），终局判定永远差一圈 →
  名次播报从不触发。改用引擎自增的 `c.run_laps`。
- **断开 / 待机后教练还在讲**：`tick` 只在 `f is None` 时早退，而游戏断开时
  dash 仍回最后一帧（`connected=False`）被当成正常帧 → 规则继续评估、继续出声。
  改成 `f is None or not f.connected` 时早退。

## 云措辞怎么配（key 放哪 / 用哪个模型）

**默认是关闭的**：不配 `--cloud` 就是纯本地模板，零外呼、零费用。
开了云润色才有下面这些事。

### 一、API key：只放环境变量，绝不进配置文件

```bash
export GT7_COACH_LLM_KEY=sk-xxxxxxxx
```

明文 key **永远不写进任何文件** —— 配置文件可以随手拷给朋友，key 留在环境里。
所以 `cloud.json` 里只写**变量名**（`api_key_env`），不写 key 本身。

百炼的语言模型和语音合成**共用同一把 key**（key 是业务空间级的，不分开授权），
所以云措辞（R2.2）和云 TTS（R3）默认都读 `GT7_COACH_LLM_KEY`。

> key 从哪来：百炼控制台 → 右上角 **API-KEY** → 创建（只显示一次，存好）。
> ⚠️ 控制台里 `ws-` 开头的那串是**业务空间 ID，不是密钥** —— 云 TTS 要它，
> 云措辞不需要，别把它当 key 填进环境变量。

### 二、模型：挑一个在「免费额度」里的

```jsonc
// cloud.json（仓库根目录有一份 cloud.example.json 可直接抄）
{
  "enabled": true,
  "provider": "dashscope",              // 百炼
  "model": "qwen3.8-flash",             // ← 想用哪个就填哪个
  "api_key_env": "GT7_COACH_LLM_KEY",   // 🔴 只写变量名
  "timeout_s": 2.0,
  "limits": { "per_lap": 1, "per_session": 30, "per_day": 300 }
}
```

告诉教练这个文件在哪，然后就不用管了：

```bash
python -m gt7coach serve --cloud /opt/gt7-coach/data/cloud.json
# 或 export GT7_COACH_CLOUD_CONFIG=/opt/gt7-coach/data/cloud.json
```

**改完不用重启**：教练每次调用前 `stat` 一次这个文件，变了就重读。
也可以在**仪表盘「赛道工程师」卡片 →「播报设置」→ 云措辞模型**里直接填
（写回同一个文件，立即生效）。

> **Docker 部署时它在哪**：容器里固定用 `/opt/gt7-coach/data/cloud.json`，
> 由 compose 的 `./data:/opt/gt7-coach/data` 挂出来持久化（这文件是运行态，
> 卡片里改的模型名写回它，容器重建不该冲掉）。
> `tools/deploy.py` 会在**文件不存在时**播种一份默认值（`enabled: true`、
> `model` 留空 = 用厂商预设的免费模型、只写 `api_key_env` 变量名），**已存在就原样保留**。
>
> 🔴 **key 不代管**：仓库里不放、部署脚本也不传。要用云措辞就自己在服务器上
> `export GT7_COACH_LLM_KEY=sk-xxx`（或写进 `/opt/gt7-coach/.env`，已 gitignore）
> 并取消 compose 里那行的注释。不填 = 纯本地模板，零外呼。

#### 填哪个？百炼的免费额度模型（2026-10 控制台）

教练的云润色用的就是 `.1` 那类**大语言模型**：

| `qwen3.8-flash` ← **默认** | 1M tokens | 2026-11-25 |
| `glm-5.3` | 1M tokens | 2026-11-23 |
| `qwen3.8-27b` / `kimi-k3` | 1M tokens | 2026-11-17 |
| `deepseek-v4-pro-0813` | 1M tokens | 2026-11-13 |
| `qwen3.8-2.4t-a95b` | 1M tokens | 2026-11-12 |

### 三、防静默扣费：默认挑免费的，配了别的会警告

- **默认模型在免费名单内** —— 不填 `model` 时用的是 `qwen3.8-flash`，
  不会因为你填了 key 就悄悄按量计费。
- **填了名单外的模型不拦，但会一直警告**：`GET /api/v1/coach/cloud` 的
  `model_warning`、以及启动横幅都会给出「可能按量计费」。仪表盘卡片里
  这条警告显示为黄字。
- 快到期（≤7 天）也会提前提醒，别等开始扣费才发现。
- 想完全确认当前状态：`curl http://127.0.0.1:8788/api/v1/coach/cloud`
  看 `model` / `model_from_user` / `model_is_free` / `model_warning` 四个字段。

> 云 TTS 的模型是**另一件事**（`--tts-model`，默认 `cosyvoice-v3-flash`）。
> 它**不在**免费名单里，`/api/v1/coach/tts` 同样会给出 `model_warning`。
> 名单里只有 `cosyvoice-v1`（10K 字符/月），但它不支持 `longanyang` 这类
> v2/v3 音色，换过去要连音色一起改 —— 没实测过，所以没动默认值。

## 部署（Docker）

```bash
git clone https://github.com/DC1024/gt7-coach && cd gt7-coach
docker compose up -d
curl http://127.0.0.1:8788/api/v1/coach/health
```

镜像基于 `python:3.12-slim`，**不装任何依赖**（整个包只用标准库）。

`network_mode: host` 是刻意的：要连宿主机的 `127.0.0.1:8787`（GT7 Dash）。
bridge 模式下这个地址指向容器自己。

**跑在哪台机器上都行**，因为出声的是浏览器：

| 部署位置 | 浏览器怎么连 | 说明 |
|---|---|---|
| 服务器（和 Dash 同一台） | `http://<服务器IP>:8788` | 最简单，仪表盘卡片默认地址就对了 |
| 玩家电脑（扬声器旁边） | `http://localhost:8788` | 少一跳网络 |

「玩家电脑」方案并不能让声音更早出来 —— TTS 是**浏览器**做的，
音频本来就是从打开仪表盘的那台机器出来的。放服务器上纯粹是为了少一个进程要管。

### 和 GT7 Dash 的启动顺序

无所谓。教练连不上 Dash 时会退避重试（2s → 15s），Dash 起来后自动接上；
反之 Dash 的卡片在教练没起时只显示「未启动」，不影响仪表盘本身。

### 部署脚本（`tools/`）

```bash
export GT7_SERVER_PASSWORD=...        # 凭据只从环境变量读，绝不进仓库
python tools/deploy.py --host 192.168.43.18 --dash-dir ../2026-10-07-02-04-04
python tools/verify.py  --dash http://192.168.43.18:8787 \
                        --coach http://192.168.43.18:8788
```

`deploy.py` 的顺序是 **备份 → 上传 → md5 硬校验 → 重建镜像 → 重启 → 再验容器内 md5**。
md5 那两步不能省：镜像里的代码靠 Dockerfile 的 `COPY` 烤进去，
"文件传到服务器了" ≠ "镜像里是这份" —— 漏了重建镜像时现象只是"新功能没生效"。

`verify.py` 走真实网络查五件事，其中**单列了 tick 速率**：
慢的依赖绝不能阻塞 tick（详见下面「已知代价」）。

### 已知代价

GT7 Dash 的 `GET /api/v1/sessions` **冷态约 11 秒**（要流式扫每个场次文件才能
给出列表里的「最快圈」，实测 5 场里有个 111 MB 的），而容器每次重启都会回到冷态。
热态是 0.01 秒。

Coach 曾经把这一句同步写在 tick 里 → 10Hz 掉到 0.3Hz、`/health` 看起来像
"服务挂了"（实际两边都正常）。**现已改为后台线程 + 独立状态**：
tick 永远不等待，`sess_state` 单独暴露（`loading` / `ok` / `empty` / `failed`），
慢接口用 40 秒超时（它不在 tick 路径上，等得起）。
实测：仪表盘冷态下 tick 仍是 10.0/s。

副作用是仪表盘重启后，教练最多要 ~11 秒才能认出「哪一场在直播」。
想让这段也消失，得把 Dash 侧的最快圈缓存落到磁盘 —— 那是 Dash 的改动，尚未做。
